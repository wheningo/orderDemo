# 延迟命令 × RocketMQ：当 Agent 说"5 分钟后关单"

> 前两篇里 agent 提议"做什么"，由领域那道墙决定"能不能做"。 这一篇 agent 学会了提议"什么时候做"——而系统必须保证两件 agent 管不了的事：**到点一定有人执行**，以及**执行的那一刻，墙还在**。
>
> 这篇几乎不贴代码。完整可运行实现都在 GitHub，文章只讲架构怎么切、心法怎么用、坑怎么踩出来的。 代码：**https://github.com/wheningo/orderDemo**

---

## 先给结论：一张责任划分表

"什么时候做"这件事，可以拆成三层。**只有最上面一层能交给 agent**，下面两层是系统和领域的责任——这张表是全文的脊柱，建议先存下来：

| 这件事 | 谁负责 | 为什么 |
|--------|--------|--------|
| **该不该延迟、延迟多久**（意图层） | ✅ 可交给 agent | 这是业务判断，agent 有上下文："这单风险低，5 分钟后再关" |
| **到点了一定有人执行**（触发可靠性层） | ❌ 系统兜底 | agent 会下线、进程会重启、消息会丢——deadline 不能依赖任何"活着"的东西 |
| **执行那一刻合不合法**（领域裁决层） | ❌ 领域兜底 | 迟到、重复、过期的触发撞上已变化的状态，必须被状态机挡回去 |

后两层就是这篇要解决的工程问题。一句话先记住：**agent 可以决定"5 分钟后关单"，但"这 5 分钟一定兑现"和"兑现时不误伤"，是系统的责任，不是 agent 的承诺。**

## 1. 一个被 cron 掩盖的问题：每条实例有自己的倒计时

前两篇的 agent 只会"现在就做"：放量、预留库存、加权曝光。但真实业务里大量需求是"等一下再做"：

- 下单后 N 分钟未付款 → 自动关单、释放库存
- 促销活动 → 定时开始 / 结束曝光加权
- TCC 预留超时 → 精确到**单条预留**的自动释放

直觉上这是 cron 的活。但 cron 的模型是"每分钟扫一次全表，把到期的挑出来"——它假设大家**共享同一个时钟节拍**。而这里 100 个订单有 100 个**各自独立**的到期时刻 T₁、T₂、T₃……，用扫表去逼近，只有两个坏结局：扫得太频繁（浪费），或精度不够（库存被多占）。

真正的需求是：**给每一条业务实例，挂一个属于它自己的、精确的闹钟。** 这一句话，就决定了后面所有的技术选型。

## 2. 心法一：面对任何 agent 命令，先做"责任分层"

这是这篇最想让你带走的东西，而且它**不止用于延迟命令**。

每次你犹豫"这个能不能交给 agent"，别笼统地纠结"信不信任 AI"，而是把这件事**拆成三个独立问题**分别回答：

1. **意图**——决定"做不做、怎么做"，需要业务上下文吗？需要 → 这层适合 agent。
2. **触发可靠性**——这件事"一定会发生"由谁保证？只要答案里出现"如果 agent 还在""如果进程没挂"，这层就**必须**从 agent 手里拿走，交给基础设施。
3. **执行合法性**——动手那一刻，状态可能已经变了。谁来做最后一道校验？永远是领域。

把延迟关单套进去：意图（5 分钟后关）可以是 agent 的判断；但"5 分钟一定到"得靠定时消息+兜底，"关的时候这单是不是已经付款了"得靠订单状态机。**三层分别由 agent / 系统 / 领域负责，互不越界。**

回看前两篇你会发现这是同一套框架的延伸：第一篇 agent 提议"做什么"、聚合裁决合法性；第二篇并发与分布式下、TCC + 那道墙仍然裁决；这一篇只是把"做什么"换成了"什么时候做"。**变的是命令的维度，不变的是责任的边界。**

## 3. 心法二：精度要匹配需求，别无脑上最高规格

确定了"每条实例一个精确闹钟"，下一步选实现。RocketMQ 给了两种延迟能力，它们的差别不是优劣，是**适用场景**：

| | 4.x delayLevel | 5.x 精确投递 |
|---|---|---|
| 精度 | 18 个固定档位（1s / 5s / … / 2h） | 任意毫秒 |
| 协议 | remoting | gRPC |
| 适合 | "大约 5 分钟后" | "精确到这一单的超时时刻" |

我两种都用——这恰恰是心法二的体现：

- agent 主动下发的"5 分钟后关单"，走**固定档位**。它不需要精确到 4min59s870ms，固定档够用、还省去维护新 client 的成本。
- 每条预留自动挂的超时释放，走**精确投递**（`setDeliveryTimestamp` 指定绝对时刻）。因为预留的超时窗口可能是 7.5 分钟这种非标准值，用固定档只能贴 5min 或 10min——**而这个偏差会直接变成库存被错误占用或提前释放**。这里精度不是奢侈品，是正确性。

**反过来说也成立：给"大约 5 分钟"的场景上毫秒精度，是在为不存在的需求付维护成本。** 精度过剩和精度不足，都是设计缺陷。

> 生产环境我用的是 RocketMQ 5.3.2，精确投递走 gRPC 协议。

## 4. 架构：一套 outbox，两条管道

很多人接消息中间件的第一反应是"再建一套发送逻辑"。但这里有个更省的解：**复用已有的 outbox，按事件类型分流。**

预留成功的那个本地事务里，本来就要写一条 `StockReserved` 事件进 outbox（前两篇的下游解耦用）。现在多写一条"超时兜底"事件即可——两条记录同一个事务，**"预留落库"和"挂上闹钟"天然原子**，要么都成、要么都不成，不需要任何额外的分布式保证。

然后让 relay 在出口处按事件类型分叉：普通领域事件走 Kafka（下游解耦），超时兜底事件走 RocketMQ 精确定时。**不是两套 outbox，是一套出口、两条管道。** 这个设计的价值不在"少写代码"，而在"少一个需要维护原子性的地方"——你没有新增任何一处"可能不一致"的接缝。

## 5. 心法三：触发源永远不可信——at-least-once + 领域幂等

这是分布式系统里最该内化的一条，延迟消息只是它的一个具体场景。

**任何外部触发——MQ、cron、agent、重试机制——都不可信。** 它可能迟到、可能重复、可能丢失、可能乱序。如果你的正确性依赖"它恰好触发一次"，那就是在沙子上盖楼。

具体到超时守卫，闹钟到点投递的那条消息，落到消费端时只做一件事：**把"该不该真的取消"这个判断，甩给领域状态机。** 消费端自己不写任何状态校验。三种情况，状态机自己收敛：

- 预留还是 `TRIED` → 真超时 → 释放库存
- 预留已 `CONFIRMED` → 用户正常付款了 → 状态机直接 no-op
- 预留已 `CANCELLED` → 别的路径取消过了 → no-op

**一条迟到的取消消息，撞上一个已经付款确认的订单，被状态机挡回去——这就是第一篇那道"墙"，在时间维度上的复用。闹钟只负责叫醒，放不放库存，永远是领域说了算。**

那 relay 重复投递怎么办（发送成功但标记完成前进程崩了，下一轮会再投一条）？**答案是：不用办。** 因为消费端幂等，重复投递就是 no-op；而万一消息真丢了，重投反而是保护。这就是 **at-least-once（至少投一次）+ 领域幂等（多投不坏事）= 不丢不错**。

为什么不追求 exactly-once？可以做——事务消息、或本地消息表加对账。但这是一笔**负收益的买卖**：消费端既然已经幂等，"恰好一次"和"至少一次 + 幂等"在结果上完全等价，你付出的双倍复杂度换来的是零。**当两个方案结果等价时，选复杂度低的那个——这本身就是一种设计能力。**

## 6. 心法四：留一手，正确性不押注于单一中间件

定时消息很好，但它有一个隐含前提：**broker 活着、消息没丢。** 这个前提在生产里不总成立。

所以前两篇那个全表扫描的 `ReservationReaper`，我没有删，而是**降级成灾备**：扫描频率从每分钟拉到每 5 分钟，超时阈值从 30 分钟拉到 1 小时。它平时几乎扫不到东西（定时消息已经把活干完了），只在 broker 宕机、消息丢失这种极端情况下，作为最后一张安全网兜住漏网的预留。

这里的心法是：**主力机制（快、精确、依赖外部 broker）和兜底机制（慢、可靠、纯本地）并存，两者互相不假设对方存在，各自幂等收敛到同一个正确结果。** 系统的正确性，不应该押注在任何单一外部组件的可用性上。

诚实地在文章和代码里保留这条灾备，比假装"上了 MQ 就万无一失"更接近真实工程——也更经得起追问。

## 7. 一个踩出来的认知：配置必须有业务含义

最后讲一个真实的坑，因为它纠正了我一个习惯。

超时窗口我第一版写死了 10 分钟。代码能跑、测试全绿——因为测试都是秒级的。直到想清楚一个场景才后背发凉：**如果用户的付款时间是 30 分钟，这条 10 分钟的闹钟会在用户还在正常付款时就把库存释放掉，造成"用户付款成功、但库存已经没了"的超卖事故。** 这种 bug 不在测试里、只在某个付款慢的真实用户身上炸。

修复不是把 10 改成 30，而是把它变成**对齐业务语义的可配置项**：超时窗口必须等于业务真实的支付窗口，部署时配置、写进 `application.yml`。

## 8. agent 主动延迟命令：意图层的真正落地

前面讲的超时守卫是"被动"兜底。agent 真正获得"时间维度"能力，是它能**主动**下发延迟命令——比如通过工具调用说"这单 5 分钟后关"。这条命令经过 Go 控制面加幂等键、限流、审计，再落到 RocketMQ 固定档位投递，到点触发订单关闭。

回到开头那张表：**agent 在这里行使的，恰恰只是"意图层"——它判断该不该延迟、延迟多久。** 而"5 分钟后这条命令一定会执行"是系统的责任，"执行时这单状态合不合法"是领域的责任。两条路径（主动命令 / 被动守卫）、两种精度、两种协议，但**最后那道裁决的墙是同一道**。

---

## 9. 我放弃了什么

技术选型的诚实，在于讲清楚没做什么、为什么：

- **没用单一协议统一两种延迟**——固定档场景用老协议更省心，两套共存的代价只是多一个依赖，各走各的互不干扰。
- **没用事务消息**——outbox 已经保证"业务落地 = 消息一定会发"，再叠事务消息是重复保证，复杂度白涨。
- **没删灾备 reaper**——多留一个定时任务，换一张"中间件挂了也不丢"的网，值。

## 收尾：贯穿三篇的一句话

| 场景 | 机制 | 精度 | 故障假设 |
|------|------|------|----------|
| agent 主动延迟命令 | 固定档投递 | 18 档 | broker 可用 |
| 预留超时自动释放 | 精确定时投递 | 毫秒 | broker 可用 → 主力 |
| broker 故障兜底 | 本地扫表 | 1h 粗扫 | broker 可能挂 → 灾备 |

三条不是冗余，精度、触发方式、故障假设各不相同，靠领域幂等收敛到同一个正确结果。

**而贯穿三篇的脊柱始终没变：agent 可以提议——做什么、什么时候做——但能不能做、到点有没有人做、做的那一刻合不合法，是系统和那道领域的墙说了算。**
